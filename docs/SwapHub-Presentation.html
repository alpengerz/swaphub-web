Opportunity

Why SwapHub exists

People already trade informally on Facebook groups and chat apps — but discovery is messy, trust is weak, and cash pressure is high. SwapHub makes barter structured, local, and safe.

The pain

  • Unused items sit idle while buyers still spend cash
  • Marketplace apps push payments & fees
  • FB groups = spam, scams, no structured offers

The insight

  • Trade-only removes escrow/KYC complexity
  • Local meetup + chat is enough for v1
  • PWA reaches Android/iOS without store delay

Positioning

  • “Carousell for barter”
  • No money in the app
  • Fair swaps, city-based discovery

Architecture

System overview

SPA talks directly to Supabase with the public anon key. Postgres RLS is the security boundary — there is no custom backend API yet.

Clients

  • Vite + React + TypeScript
  • Tailwind UI (mobile + desktop)
  • React Router app shell
  • vite-plugin-pwa (service worker)
→

Supabase platform

  • Auth — email/password, confirm email
  • Postgres — listings, offers, trades, chat
  • Storage — listing photos, avatars
  • Realtime — messages / conversations
  • RLS + triggers — authorization & rate limits

Hosting

Vercel CDN + SPA rewrites + security headers (CSP, frame deny)

Email (needed)

Custom SMTP via Resend (or Brevo) — free Supabase SMTP ≈ 2/hr

Domain (needed)

Own domain for branded mail + later custom URL

Data model

Core entities

Identity

  • profiles
  • username, city, bio, avatar
  • email_verified (auth-synced)

Marketplace

  • listings + listing_photos
  • status: active / reserved / traded / hidden
  • looking_for, category, condition

Trade & trust

  • offers → trades
  • conversations + messages
  • reviews, reports

Key business rules (enforced in DB)

  • No offers on your own listing
  • Only listing owner can accept an offer
  • Offered items must be your active listings
  • Conversation seller must be listing owner
  • Reviews only after completed trade
  • Storage uploads scoped to {userId}/…
  • Write rate limits (messages/offers/listings/reports)
  • Content length constraints
Security posture

Guardrails in place

Already handled

  • RLS on all app tables
  • No service-role key in frontend
  • No raw SQL from client (PostgREST)
  • React XSS escaping (no dangerous HTML)
  • Seller-only accept + offer validation
  • Email verification gate in app
  • CSP / nosniff / frame deny on Vercel
  • PWA caches static assets only

Still operational (you must do)

  • Connect Resend SMTP + raise email rate limits
  • Buy/verify a sending domain
  • Keep Confirm Email ON in Auth settings
  • Optional later: Cloudflare in front of custom domain

DB guardrails are already live. DDoS: SPA alone can’t stop traffic floods — edge + Supabase limits + DB throttles are the layers.

  • Custom SMTP + domain

  • Admin view for reports

  • Pagination UI + infinite scroll
  • Push notifications (web push)
  • Post-trade review UI
  • Better search (full-text / ranking)
  • Moderation tools + block user
  • Analytics (Plausible/PostHog)

Later (P2)

  • Expo native wrappers / store listing
  • Reputation scoring polish
  • Meetup safety features
  • Multi-city growth tooling
  • Edge Functions for heavy logic
  • AWS only if 50k–100k+ users

Recommendation

Ship the PWA beta. Don’t rebuild.

Keep the current architecture (Vercel + Supabase). Finish SMTP/domain ops, invite a small city cohort, and only go native stores after retention is real.
